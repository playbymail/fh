# Phase 2 Plan — `fh` from renderer to simulator

> Supersedes the issue-#1 umbrella body and the prior #2–#5 issue set. Drives the
> GitHub epic and its implementation issues. No code is written by this document.

## 1. Current state ("the hole")

`fh` today is a **renderer, not a simulator**. The only validated path is:

```
fhc computes the turn -> `fhc export json` (galaxy.json, systems.json, species.NNN.json)
   + sp0X.log + locations.dat
   -> fh ingests into a Store -> fh re-renders sp0X.rpt.tN -> diff vs fhc reference
```

Grounded in the code:

- **Pluggable store — done.** `internal/data/store` has three backends
  (`binarystore.go`, `jsonstore.go`, `sqlitestore.go`) behind a deliberately tiny
  `Store` interface (`IngestWorld` / `LoadWorld` / `Close`), resolved via
  `factory.go` from a game dir's `far-horizons.json`. SQLite uses ZombieZen +
  `sqlitemigration` per `MIGRATIONS.md`. Round-trip and cross-backend parity tests
  pass.
- **Ingest — done (one-way).** `internal/engine/ingest.go` →
  `internal/data/fhjson.ReadWorld` builds a `model.World` from `fhc`'s exported
  JSON + logs + `locations.dat`. This consumes **post-turn** state; there is no
  pre-phase ingest/replay loop.
- **Renderer — done.** `internal/engine/report.go` (+ `report_orders.go`) renders
  `sp0X.rpt.tN` byte-identical to `fhc` for turn 1, all 4 species, all 3 backends
  (`report_test.go`, `store_parity_test.go`).
- **RNG — done.** `internal/engine/rng` (xoroshiro + `algorithmm.go`) with committed
  golden vectors. Not yet proven to reproduce `fhc`'s *state-generating* sequence
  inside a phase.
- **Engine struct — minimal.** `internal/engine/engine.go` holds `store`, `rng`,
  `gameID` and methods for ingest/load/render only. No package-level mutable game
  state (good — the Phase-2 invariant). No phase execution.
- **CLI — stubs.** In `cmd/fh/main.go`, `fh run combat|finish|jump|post-arrival|
  pre-departure|production` all return `cerrs.ErrNotImplemented`. `create reports`,
  `import json`, store creation work. `inspect`, `list`, `scan`, `stats`, `turn`,
  `export snapshot` are stubs.
- **Model — read-shaped.** `internal/model/types.go` (`World`, `Galaxy`, `System`,
  `Planet`, `Nampla`, `Ship`, `Species`, `Location`) carries the fields the renderer
  needs. It is not yet proven sufficient for *mutation* by every phase (e.g.
  transaction log, combat outcomes, build queues, per-turn deltas).
- **Scaffolding — unused.** `internal/engine/{world,orders,effects,schedule}` are
  stubs from the original plan; `CLAUDE.md` says do not build on them without
  checking. Treat as replaceable.

The oracle (`internal/game` / `cmd/fhc`) is **done and frozen**: file-faithful C
port, 36 `do_*` commands, full pipeline, validated by `turn_pipeline_test.go`
(4 accumulating turns) and `scenario_test.go` (build / jump / transfer / combat)
against `testdata/cref/` generated by `generate.sh`. **It must never change.**

## 2. Goal state and definition of done

**Parity contract:** for the same seed and the same orders, `fh`'s `sp0X.rpt.tN`
reports are **byte-identical** to `fhc`'s. Reports are the only parity surface —
`.dat`/s-expr formats are not part of `fh`'s contract. State lives in the `Store`;
no package-level mutable globals (state on the `Engine` struct, threaded
explicitly); any state-generating RNG reproduces `fhc`'s exact sequence.
`internal/game` / `cmd/fhc` are untouched.

**Definition of done for a phase:** the phase's orders parse and execute, mutating
`model.World` (persisted via the Store), and for **both** (a) the committed scenario
fixtures that exercise the phase and (b) the 4-turn default-orders pipeline, the
resulting `sp0X.rpt.tN` reports match `fhc` byte-for-byte. Until then the phase is
not done — order parsing without execution, or execution without report parity,
does not count.

## 3. The critical prerequisite — the parity harness

Today's tests (`report_test.go`, `store_parity_test.go`) ingest `fhc`'s
**post-turn** state and re-render. That validates the renderer, not `fh`'s
computation. The harness this phase needs:

1. **Pre-phase ingest → run phase → diff.** Ingest the **pre-phase** state (the
   state `fhc` had *before* running phase X), run `fh`'s phase X (consuming that
   phase's orders), then diff `fh`'s resulting `sp0X.rpt.tN` against `fhc`'s
   **post-phase** reference reports. This is the inverse of the current flow and is
   the gate that proves `fh` computes the same result as `fhc`.
2. **Relationship to the existing `fhc` harness.** It mirrors `generate.sh`'s
   staging: `generate.sh` already snapshots `setup/` and `turn1..4/`, and runs the
   scenarios from a fresh post-setup state. The new harness reuses those *same*
   `testdata/cref/` snapshots as pre/post state — it does not generate new C data.
   Where the C-side `turn_pipeline_test.go` chains phases through `.dat` files in one
   process, the `fh` harness chains phases through the **Store** (load World → run
   phase → persist World), one `Engine` per game.
3. **Pre-phase reference snapshots.** `generate.sh` currently snapshots only between
   *turns* (post-`report`), not between *phases* within a turn. To diff a single
   phase, the harness needs the World state immediately before that phase. Two
   options, decide in the harness issue: (a) ingest the previous phase's `fhc` state
   where a snapshot already exists (turn boundaries) and build inner phases up
   incrementally; or (b) extend `generate.sh` with per-phase `fhc export json`
   snapshots inside a turn (e.g. `turn1.pre-jump/`). Option (b) gives true
   single-phase isolation and is recommended; it is additive to `generate.sh` and
   changes no `fhc` behavior.
4. **Commit `fh`-side scenario fixtures.** Mirror
   `testdata/scenarios/{build,combat,jump,transfer}` for the `fh` harness (the order
   `.ord` files are already committed and shared; the `fh` harness consumes the same
   fixtures). Wire into `go test`, skipping when `testdata/cref` is absent (same
   pattern as today).
5. **Multi-turn accumulation.** Drive 4 accumulating turns end-to-end through `fh`
   (Store carried across turns), mirroring `turn_pipeline_test.go`, and diff the
   turn-N reports.

This harness is the first issue of the work and **blocks every phase**.

## 4. The work — fine-grained sub-tasks

Each pipeline phase decomposes into: **(a) order-parser support** for that phase's
order verbs, **(b) per-command execution** (`do_*` logic), **(c) phase-level state
mutation / sequencing** (the `*.go` phase driver: ordering, RNG draws, transaction
emission, log lines), and **(d) the render-parity gate** (scenario fixture + 4-turn
pipeline). C source and gate fixture are named per phase.

**Order → phase map (from the C port):**

- **Combat** (`combat1.go`, `combat2.go`, `intercept.go`): combat verbs
  `ATTACK`/`HIJACK`/`ENGAGE`/`HIDE` parsed in the combat phase itself;
  `AMBUSH`/`INTERCEPT` are *set up* in the production phase but resolved in combat.
  Gate: `combat` scenario (3-turn).
- **Pre-departure** (`predeparture.go`): `ALLY BASE DEEP DESTROY DISBAND ENEMY
  INSTALL LAND MESSAGE NAME NEUTRAL ORBIT REPAIR SCAN SEND TELESCOPE TRANSFER UNLOAD
  VISITED WORMHOLE`. Gate: `transfer` scenario + defaults.
- **Jump** (`jump.go`): `JUMP MOVE VISITED WORMHOLE`, with mishap RNG. Gate: `jump`
  scenario (2-turn).
- **Production** (`production.go`): `ALLY AMBUSH BUILD DEVELOP ENEMY ESTIMATE HIDE
  INTERCEPT NEUTRAL PRODUCTION RECYCLE RESEARCH SHIPYARD UPGRADE`. Gate: `build`
  scenario + defaults.
- **Post-arrival** (`postarrival.go`): `ALLY DEEP DESTROY ENEMY LAND MESSAGE NAME
  NEUTRAL ORBIT REPAIR SCAN SEND TEACH TECH TELESCOPE TERRAFORM TRANSFER`. Gate:
  defaults / re-verify.
- **Locations** (`location.go`): no orders; recompute the per-species location index
  from World state. Gate: defaults.
- **Finish** (`finish.go`): no orders; end-of-turn bookkeeping (econ units,
  `max_tech_level`, population). Gate: defaults.
- **Report** (`report.go`): done; re-verify after every phase lands.

All **36 `do_*` commands** are covered across the phases above: `ALLY AMBUSH BASE
BUILD DEEP DESTROY DEVELOP DISBAND ENEMY ESTIMATE HIDE INSTALL INTERCEPT JUMP LAND
MESSAGE MOVE NAME NEUTRAL ORBIT PRODUCTION RECYCLE REPAIR RESEARCH SCAN SEND SHIPYARD
TEACH TECH TELESCOPE TERRAFORM TRANSFER UNLOAD UPGRADE VISITED WORMHOLE`.

**Shared foundations (cross-cutting, needed before per-command work):**

- An **order lexer/parser** (`fh`-side, idiomatic; the C reads tokens lazily
  mid-execution — `fh` should parse to a typed order list per species, normalized,
  then dispatch). One parser, extended phase-by-phase.
- **World mutation support**: extend `model.World`/`Species`/`Nampla`/`Ship` and the
  Store schema with whatever the phases mutate but the renderer never read —
  inter-species transaction log, message bodies, build/upgrade deltas, combat
  results, alliance/enemy bit updates, per-turn log accumulation (`Species.Log`).
  Append-only SQLite migrations only.
- A **phase-runner abstraction** on `Engine`: `RunCombat/RunPreDeparture/RunJump/
  RunProduction/RunPostArrival/RunFinish/RunLocations(ctx)` that load → mutate →
  persist, plus the per-species `spNN.log` emission the report prepends.

## 5. Dependency ordering / sequencing

1. **Harness + fixtures + model/Store mutation scaffolding** come first — nothing
   can be validated without them.
2. **Order parser** before any per-command execution within a phase.
3. **Phases in pipeline order**: locations → combat → pre-departure → jump →
   production → post-arrival → finish → report re-verify. Earlier phases produce
   state later phases consume; the default-orders 4-turn pipeline only goes green
   once all phases land.
4. Within a phase: parser support → per-command execution → phase sequencing/RNG/log
   → parity gate.
5. **Report re-verify** runs continuously (it is the gate), with a final dedicated
   pass after finish.
6. CLI `run/replay/diff`, extra report formats, and CI/perf/release polish ride
   alongside but the `run` subcommands become meaningful only as phases land.
